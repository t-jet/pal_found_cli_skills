# Ontology and Compute Module development

[Back to Foundry development topics](../SKILL.md)

Use this reference when designing an operational data model, writing Ontology logic, or running custom container code in Foundry. An Ontology models business entities and decisions; a Compute Module runs containerized code as a callable function or as part of a data pipeline. Their security and execution lifecycles differ.

## Model the Ontology

An **object type** defines an entity or event, such as `Shipment`; each object is one instance. **Properties** hold typed values, while **link types** define relationships between object types, such as `Shipment` to `Warehouse`. **Action types** define user-initiated edits and side effects. Functions add code-based logic that can accept objects or object sets. Object Views present an object's information and related workflows. This model connects datasets and logic to operational applications; changing a dataset schema alone does not define an Ontology action. See [core concepts](https://www.palantir.com/docs/foundry/ontology/core-concepts) and the [types reference](https://www.palantir.com/docs/foundry/object-link-types/type-reference).

Start with stable business identities and the relationships users need to traverse. When creating an [object type](https://www.palantir.com/docs/foundry/object-link-types/create-object-type), choose its backing data, primary key, display properties, and property mappings deliberately. The key determines which records represent the same object; changes to mappings or key semantics can affect links and application behavior. Choose property [base types](https://www.palantir.com/docs/foundry/object-link-types/base-types) that match source values and the intended filters or calculations. A [shared property](https://www.palantir.com/docs/foundry/object-link-types/shared-property-overview) gives several object types one consistent property definition. A [link type](https://www.palantir.com/docs/foundry/object-link-types/link-types-overview) describes the relationship and its cardinality; verify its join keys against real data before exposing it to users. [Object type groups](https://www.palantir.com/docs/foundry/object-link-types/type-groups) organize types, while [type classes](https://www.palantir.com/docs/foundry/object-link-types/metadata-typeclasses) convey metadata-driven meaning to consuming applications.

An **interface** defines a common shape and capabilities that multiple object types implement. For example, `Truck` and `Vessel` can implement a `TransportAsset` interface so an application can work with either type through common properties and links. Implementations must map the interface members to the concrete type. Use an interface when a consumer genuinely needs polymorphism; a shared property alone does not express the full common contract. See [interfaces](https://www.palantir.com/docs/foundry/interfaces/interface-overview) and [implementing an interface](https://www.palantir.com/docs/foundry/interfaces/implement-interface).

## Read and query objects

An **object set** is a collection of objects defined by a type and optional filters, links, or other operations. It can be evaluated to fetch objects or aggregated to answer questions such as counts by status. Query only the fields and result scope the application needs; large traversals and aggregations consume Ontology query capacity. Distinguish a dynamic object-set expression from a saved, static selection when choosing whether results should follow later data changes. See [Object Set basics](https://www.palantir.com/docs/foundry/api/ontologies-v2-resources/ontology-object-sets/ontology-object-set-basics), [saved Object Sets](https://www.palantir.com/docs/foundry/analytics/datasets-object-sets), and [query compute](https://www.palantir.com/docs/foundry/ontologies/query-compute-usage).

For application code, use the [TypeScript OSDK query model](https://www.palantir.com/docs/foundry/ontology-sdk/typescript-osdk) for object reads, links, filters, and aggregations. Inside Foundry Functions, object-set APIs support searches and aggregation; the [Functions Object Sets reference](https://www.palantir.com/docs/foundry/functions/api-object-sets) describes the TypeScript v1 form, so check the [language feature matrix](https://www.palantir.com/docs/foundry/functions/language-feature-support) before translating an example to TypeScript v2 or Python. A shipment queue, for instance, can filter `Shipment` objects by status, follow their warehouse links, and aggregate by destination instead of loading every object into application memory.

## Write through Actions and Functions

An **Action** is the operational write boundary. Define typed [parameters](https://www.palantir.com/docs/foundry/action-types/parameter-overview), [rules](https://www.palantir.com/docs/foundry/action-types/rules) that create or edit objects and links, [submission criteria](https://www.palantir.com/docs/foundry/action-types/submission-criteria) that validate when it may run, and [permissions](https://www.palantir.com/docs/foundry/action-types/permissions) that control who may apply it. For a `Dispatch shipment` action, parameters might include a shipment and destination; criteria can reject an invalid state before rules edit its status and link. Read and write authorizations govern what data action logic can access and change; application UI checks do not replace these controls. See [Action overview](https://www.palantir.com/docs/foundry/action-types/overview) and [read/write authorizations](https://www.palantir.com/docs/foundry/action-types/read-write-authorizations).

Use a [function-backed Action](https://www.palantir.com/docs/foundry/action-types/function-actions-overview) when rules need code-based logic, and inspect its edit scope before publishing. A [writeback webhook](https://www.palantir.com/docs/foundry/action-types/webhooks) runs before Ontology changes: if its external request fails, the action stops, but an external success can still be followed by an Ontology failure. A side-effect webhook runs after object changes and may complete after the user sees success. Design external consumers for retries and reconciliation; neither mode promises one atomic transaction across Foundry and the external system. [Side effects](https://www.palantir.com/docs/foundry/action-types/side-effects-overview) also include other post-submission behaviors.

**Functions** are reusable typed code that can read Ontology objects and object sets, return query results, or prepare edits for Actions. Develop in a Functions repository, run and test in development, then publish a version for consumers. Match supported input/output types and language features before choosing TypeScript v1, TypeScript v2, or Python. Use [Functions getting started](https://www.palantir.com/docs/foundry/functions/getting-started), [types](https://www.palantir.com/docs/foundry/functions/types-reference), and [language support](https://www.palantir.com/docs/foundry/functions/language-feature-support). Ontology edits differ by runtime: follow the specific [TypeScript v2](https://www.palantir.com/docs/foundry/functions/typescript-v2-ontology-edits) or [Python](https://www.palantir.com/docs/foundry/functions/python-ontology-edits) guide rather than mixing APIs from TypeScript v1 examples. Test object searches, edit proposals, and identity-dependent rules before publishing. For TypeScript v1 Functions, the [Object Set stubs](https://www.palantir.com/docs/foundry/functions/unit-test-object-searches), [edit tests](https://www.palantir.com/docs/foundry/functions/unit-test-ontology-edits), and [user/group mocks](https://www.palantir.com/docs/foundry/functions/unit-test-users-groups) show the supported unit-test approach. Follow the runtime-specific guides for other languages.

## Secure Ontology consumers

New Ontologies can use Foundry project-based permissions for Ontology resources. Existing Ontologies require an owner to enable this model and migrate resources; it is not yet available for Default Ontologies. Check the actual Ontology's configuration. Permission to view an object type's schema does not itself grant access to its objects. Object visibility also depends on the backing datasource or configured object/property security policy. Action permissions and read/write authorizations are separate checks. Test with accounts representing intended users, including restricted users; an administrator's successful query does not prove application access. See [Ontology permissions](https://www.palantir.com/docs/foundry/object-permissioning/ontology-permissions), [object security policies](https://www.palantir.com/docs/foundry/object-permissioning/object-security-policies), and [Action permissions](https://www.palantir.com/docs/foundry/action-types/permissions). Older Ontology-role and datasource-derived models are documented under [legacy permissions](https://www.palantir.com/docs/foundry/object-permissioning/ontology-permissions-legacy).

## Run custom code with Compute Modules

A **Compute Module** deploys a Docker image as isolated, scalable containers in Foundry. Its entry-point container handles work, and a replica may contain additional containers. Replicas cannot share in-memory state, so persist required state in a suitable external or Foundry resource. Use a module for an existing library, language, or model that needs a container runtime; native Functions and transforms may be simpler for logic they support directly. See the [overview](https://www.palantir.com/docs/foundry/compute-modules/overview), [containers](https://www.palantir.com/docs/foundry/compute-modules/containers), and [getting started](https://www.palantir.com/docs/foundry/compute-modules/get-started).

Choose an [execution mode](https://www.palantir.com/docs/foundry/compute-modules/execution-modes) from the workload:

| Mode | How work runs | Data access and provenance |
| --- | --- | --- |
| Function | Foundry applications or Functions call registered container-backed functions. Suitable for interactive inference or other request/response logic. | Without platform permissions, code cannot call Foundry APIs. Where available, application permissions use the module application's service user, so access is independent of the invoking user's own permissions. |
| Pipeline | Foundry's build system supplies declared inputs and manages outputs. Suitable for continuous or scheduled ingestion and processing. Users do not directly query the module. | A job token is scoped to declared input/output resources; the build system records their lineage and manages output dataset transactions. |

In pipeline mode, declare every needed input and output explicitly. The module has no default access to Foundry resources; supported configured resources include datasets, streaming datasets, and media sets in the module's project. The build system mounts a scoped token and a resource-alias map into the container. Read these at runtime instead of hard-coding credentials or resource identifiers. Output dataset transactions are committed when the pipeline run succeeds. See [pipeline execution](https://www.palantir.com/docs/foundry/compute-modules/execution-modes).

Compute Modules start with no external network access, including access to other Foundry services. Configure a [Data Connection source](https://www.palantir.com/docs/foundry/compute-modules/sources) with the required network policy and secrets, and allow its import into the module. The source must be in the same project. This is separate from granting Foundry resource permissions through function-mode application permissions or pipeline-mode job tokens. Avoid putting secrets into the image, logs, or function arguments.

Develop and test the image locally, then publish and configure it in Foundry following [getting started](https://www.palantir.com/docs/foundry/compute-modules/get-started). Use the [Python SDK](https://www.palantir.com/docs/foundry/compute-modules/python-sdk) or [TypeScript SDK](https://www.palantir.com/docs/foundry/compute-modules/typescript-sdk) for supported client contracts; register functions as described in [Compute Module functions](https://www.palantir.com/docs/foundry/compute-modules/functions). If a module needs Ontology data, follow [OSDK integration](https://www.palantir.com/docs/foundry/compute-modules/osdk-integration) and its execution-mode identity rules. Configure [replica minimums, concurrency, and scaling](https://www.palantir.com/docs/foundry/compute-modules/scaling) for expected load; pipeline modules with no interactive queries may scale to zero unless a minimum replica is set. Monitor requests, failures, and resource use through [Observability](https://www.palantir.com/docs/foundry/observability/overview), and review [usage](https://www.palantir.com/docs/foundry/compute-modules/usage) before fixing capacity values.
